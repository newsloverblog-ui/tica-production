# Tica production operations runbook

This is the minimum operating contract for the transactional platform. Replace example paths and addresses before deployment. Do not enable live payouts or additional gateways merely because the application boots.

## Required topology

- PHP 8.3, 8.4 or 8.5 with the locked Laravel 13 dependency set. The release-readiness gate rejects older runtimes and untested PHP 8.6+ runtimes.
- MySQL with encrypted backups and point-in-time recovery where available.
- Shared Redis for cache, sessions, locks, rate limits and the `payments` and `default` queues.
- Two independently supervised worker groups. `payments` must not share its only capacity with exports or mail.
- Exactly one scheduler leader running `artisan schedule:run` every minute.
- A production SMTP/API mail transport.
- At least one off-server incident destination: `OPS_INCIDENT_EMAIL` or a signed HTTPS `OPS_INCIDENT_WEBHOOK_URL`.
- Independent monitoring that meets `docs/external-observability-standard.md`: exact liveness/readiness probes, privacy-scrubbed error tracking and a financially safe synthetic checkout with exercised alert routing.
- `REFUND_RECOVERY_ALERT_MINUTES` defines when a provider refund still missing from Paystack reconciliation becomes an off-server critical incident (minimum 10 minutes; default 30).
- HTTPS from the public load balancer through every authenticated/payment endpoint.

Templates live in `deploy/supervisor/tica-workers.conf.example` and `deploy/cron/tica-scheduler.example`.

## Required secrets and safety flags

Generate independent random values for `APP_KEY`, `TICKET_SIGNING_KEY`, gateway secrets and `OPS_INCIDENT_WEBHOOK_SECRET`. Never rotate `TICKET_SIGNING_KEY` without a ticket migration plan. Keep:

```dotenv
APP_ENV=production
APP_DEBUG=false
QUEUE_CONNECTION=redis
CACHE_DRIVER=redis
SESSION_DRIVER=redis
PAYSTACK_TRANSFERS_ENABLED=false
PAYOUT_AUTOMATIC_RELEASE_ENABLED=false
WEB_INSTALLER_ENABLED=false
WEB_UPDATER_ENABLED=false
```

Only enable Paystack transfers after the sandbox transfer/webhook/reversal drill passes and the finance alert recipient is verified. `PAYOUT_AUTOMATIC_RELEASE_ENABLED` stays false until eligibility and risk policy are implemented and approved. Web installer/updater routes are unconditionally blocked in production; database migrations belong in authenticated CLI/CI deployment, never a public HTTP workflow.

Payout disputes are support evidence, not payout actions. Finance must reconcile the withdrawal, transfer, settlement and bank/provider evidence before responding. Moving a dispute to under review, resolved or rejected never changes the withdrawal status or organizer balance; use only the separate controlled withdrawal actions after reconciliation. A closing response must explain the result without including bank credentials or secrets, and a second dispute cannot be opened while one remains active.

Follow `docs/security-assurance-and-incident-drill.md` before launch. Release readiness requires CSP enforcement, a current penetration-test reference, a documented key rotation and a real off-server incident exercise. Never insert secrets or raw report content in environment evidence fields.

Event refunds for Paystack and Flutterwave are provider-submitted controls, not immediate accounting overrides. Finance must use the transaction screen, wait for a terminal provider success, and investigate `verification_required`, `needs_attention` or failed states through `payments:reconcile-refunds`. Flutterwave's initial `completed` response means the refund was initiated but may still be awaiting customer disbursement; never manually mark it processed. A checked-in admission must use the refund-dispute queue. Review the immutable scanner evidence and written exception, record a meaningful resolution, then approve or reject the case. Approval creates one controlled provider refund but never erases the check-in and never moves money locally before provider confirmation. Do not create a manual refund alongside an open, under-review or refund-queued case.

Enabling a certified online gateway also activates a production-drill release gate. Assign `PAYMENT_OPERATIONS_OWNER_EMAIL` and exercise every enabled provider from the production-like MySQL/worker environment: event checkout, signed webhook and replay, lost-browser-callback recovery, reservation expiry/restoration, provider refund through terminal local accounting, and daily reconciliation. Paystack enablement additionally requires the hardened shop checkout/refund path. Record `PAYMENT_PRODUCTION_DRILL_AT`, a non-secret evidence reference and only the scenario flags actually proven by provider, database, queue and ledger evidence. A stale, partial or provider-mismatched drill blocks release; configuration is an attestation and must not be invented to clear the gate.

Paystack event checkout generates the transaction reference locally and persists the encrypted intent and ticket reservation before contacting Paystack. Initialization uses the bounded shared gateway client and accepts redirects only from the exact HTTPS `checkout.paystack.com` host. A timeout or upstream server error becomes `verification_required`: keep the reservation, use the signed recovery screen and verify the same reference; never start a second charge. A definitive rejection marks the intent failed and releases its reservation. The browser return performs one authoritative provider verification and then completes or enters signed recovery—it does not wait in a polling loop and never reconstructs a payment from session/cache data. Signed webhooks likewise require the durable local intent and gateway-scoped ledger identity.

Free-ticket confirmation is also a transaction, even though no money moves. The reviewed checkout session creates one server-held submission identity; its hash is unique on `bookings`, and a retry returns that booking instead of decrementing inventory or issuing another QR. Invoice generation and confirmation mail run through the monitored booking-delivery queue. If the browser loses the response, retry the same submission rather than starting a new ticket selection; if delivery fails, repair the queue/document/mail dependency and let the existing job retry rather than creating another booking.

`bookings:monitor-deliveries` scans every durable delivery family in bounded batches so a provider-wide outage cannot exhaust the scheduler process by materializing the entire incident population. The default is 100 records per family per run; operators may use `--batch-size=1..500` when draining a verified backlog. A non-zero result means at least one exhausted delivery was found in the processed batch. Off-server incidents contain only stable record identifiers, attempt counts and a boolean failure-recorded signal; decrypted delivery errors stay in the encrypted application ledger for authorized review and must never be copied into email, webhook or log payloads. Repair the dependency and run the monitor repeatedly until its summary and exit status are clear; do not increase the batch size beyond the enforced ceiling or bulk-edit `alerted_at` to hide backlog.

Ticket SMS is a separate one-attempt `payments`-queue delivery because a provider timeout may have accepted the message even when the application received no response. Never requeue an ambiguous failure automatically. First verify Termii's activity and retain a non-secret case/evidence reference. When the provider accepted the original request, reconcile it without resending with `php artisan tickets:recover-sms-delivery DELIVERY_ID --accepted-reference=PROVIDER_MESSAGE_ID --evidence=CASE_REFERENCE`. Only when Termii confirms that it did not accept the request may one replacement be queued with `php artisan tickets:recover-sms-delivery DELIVERY_ID --confirm-not-accepted --evidence=CASE_REFERENCE`. The command accepts only failed SMS rows, locks the row, rejects reused provider message IDs and audits either decision.

Production readiness requires more than valid Termii credentials. The assigned `TICKET_SMS_OWNER_EMAIL` must retain current evidence that local and international formats delivered, a rejected number failed clearly, a forced timeout raised the ambiguity incident without duplicate delivery, the signed URL opened the exact booking, and the `payments` worker met the delivery target. Record the exercise date/reference and individual scenario flags only after checking provider and application evidence; never set them merely to clear the gate.

Flutterwave event checkout follows the same durable recovery boundary. The Tica-owned reference, encrypted intent and ticket reservation exist before the hosted-payment request, and only the exact HTTPS `checkout.flutterwave.com` redirect is accepted. Connection loss, timeout, throttling or a provider server error is an unknown outcome: the intent becomes `verification_required`, inventory stays reserved and operators/customers must verify the original reference instead of initiating another charge. Browser-supplied callback status is never trusted. The throttled callback and signed webhook both verify status, reference, amount, currency and customer data directly with Flutterwave; only an authoritative failed, cancelled or reversed state releases inventory, while pending/processing states remain recoverable. Fulfilment and duplicate detection use the gateway-scoped ledger identity.

Event cancellation is a controlled workflow, not an event-status edit. An organizer or authorized administrator submits a cancellation request; this immediately freezes new sales and releases active ticket reservations. Finance/operations must review the cancellation queue and its estimated impact before approval. Approval, rejection, checked-in dispute creation and manual-case resolution require both Event Management and Transaction permissions; event managers without Transaction access have a read-only evidence view and must not borrow a finance account. Approval queues eligible Paystack/Flutterwave refunds through the normal asynchronous provider workflow and creates a per-booking manual-review case for checked-in, legacy, unsupported or conflicted payments. Rejection restores the event's previous visibility and resumes suppressed paid-booking fulfilment. Attendee notices have their own durable delivery ledger and are monitored by `bookings:monitor-deliveries`. Resolve every manual-review case from the cancellation ledger: use checked-in dispute review where admission exists; after repairing a hardened sale-ledger identity, retry the controlled provider path; for legacy payments, record an external refund only after independently verifying the unique bank/provider receipt; otherwise close with a meaningful no-refund resolution. Each terminal outcome refreshes the cancellation totals, audits the decision and re-queues a customer-safe outcome notice. Parent-bound case-ledger exports are private point-in-time finance evidence: they exclude customer contact data and free-text reasons/resolutions, expire automatically and can be downloaded only by the requesting administrator through a short-lived signed link. Never directly flip the event back to active and never issue a duplicate manual refund while a provider refund or dispute is pending. Late verified payments for an already approved cancellation are attached to the same refund ledger automatically.

For event-day reconciliation, use the private check-in ledger from the organizer export screen or scanner workspace. Only organizers and gate supervisors may request it; check-in-only staff cannot. The snapshot contains accepted admissions and occurrence-counted duplicate attempts with ticket/booking references, timestamps, source, original/attempted enrolled devices and authenticated staff identity. New accepted admissions persist the authoritative `scanner`, `manual` or `offline_sync` source; a blank historical source means the admission predates source attribution and must not be guessed. It deliberately excludes attendee names, email, phone and free-text conflict notes. Treat an old ledger as a point-in-time record, not live attendance: queue a new one after later scans. Let the default worker complete it, download only through the requesting actor's short-lived signed link, and never copy the file to public storage. A missing staff value represents a historical/organizer-driven admission that predates attributable scanner staff; do not fabricate an identity.

Online product-shop checkout is production-enabled only for Paystack. It uses its own durable product payment intent, authoritative stock hold, signed webhook plus server verification, session-independent recovery, idempotent accounting/fulfilment and provider-submitted full-refund contract. Keep every other online shop gateway disabled; the application allowlist rejects them even if an operator activates their legacy database record. A successful manual submission still reserves physical stock, and rejecting a still-unpaid manual order releases it exactly once. Administrators cannot manually mark durable online intents paid or downgrade them; those transitions belong exclusively to verified gateway and refund workflows.

The release-readiness command also checks that the application-owned transactional tables for payment intents, product intents, refunds, checked-in refund disputes, ticket reservations, ticket-transfer delivery, organizer and customer email-verification delivery, event waiting lists, organizer guest invitations, corporate registration forms/templates/questions/submissions/attendees/answers/notifications/imports/import rows/sponsor allocations/allocation claims/agenda sessions/session selections/company invoices/badge settings/embed settings, payout transfers, payout disputes, event cancellation requests/cases/notifications, delivery state, incidents and audit history are present. It also requires the event lifecycle, registration mode, registration-question ticket scope, registration import/allocation linkage, invoice-to-booking linkage, refund-to-cancellation linkage, refund-to-dispute linkage, ticket-transfer delivery state, organizer/customer email-verification delivery state and cancellation-case resolution/evidence columns. Safety-critical database constraints are checked separately; the SMS provider message identity must retain its named unique index so a partially applied migration cannot silently permit duplicate reconciliation evidence. A reachable database with pending safety-contract migrations is therefore not considered deployable. `EVENT_REGISTRATION_IMPORT_DISK` and `EVENT_REGISTRATION_INVOICE_DISK` must resolve to private storage outside the public web root.

Before the first ticket-unit release, and after any controlled historical repair, run `php artisan tickets:audit-booking-units`. It is read-only, returns a non-zero exit code while any booking is unsafe, and reports a bounded sample of booking references plus issue categories. When the only issue is `missing_units`, run `php artisan tickets:issue-booking-units`, review every reported failure, and audit again. Do not run a bulk SQL insert or fabricate the remainder of a partial set. Count/sequence, event, organizer, ticket or variation contradictions require evidence-led reconciliation and an approved change because silently guessing can create extra valid admission credentials. `ops:release-readiness` independently audits the full population and remains critical until every booking has exactly the expected immutable unit set. The scanner also revalidates the complete set under its row locks; a `ticket_units_inconsistent` gate response is a supervisor escalation, never permission to admit manually or edit `scan_status`.

The payment-intent sensitive-field migration changes both event and product intent `email` columns to text and encrypts buyer email plus provider diagnostic fields with a versioned prefix. Back up the database before applying it and keep `APP_KEY` stable through deploy and rollback. The migration is transactional per ledger, is safe to rerun after a rolled-back failure, and its `down` path decrypts before restoring the previous schema. `ops:release-readiness` reports `security.payment_intent_sensitive_fields_encrypted` as critical until both schemas are current and no legacy plaintext row remains.

The finance diagnostic-field migration applies the same versioned encryption contract to `last_error` on event refunds, product refunds, payout transfers, gateway settlements and payment-reconciliation runs. Back up the database and keep `APP_KEY` stable while applying or rolling back it. The migration processes each ledger in bounded transactional batches, model reads remain transparent, and `ops:release-readiness` reports `security.finance_diagnostics_encrypted` as critical if any required schema is missing or any nonempty diagnostic remains plaintext.

The operational diagnostic-field migration extends that contract to booking delivery, ticket resend, customer and organizer verification delivery, data export and schedule, ticket transfer, event-cancellation notification, registration import and notification, waitlist and product-order delivery ledgers. Back up the database and keep `APP_KEY` stable while applying or rolling back it. The migration processes all twelve tables in bounded transactional batches and is reversible; `ops:release-readiness` reports `security.operational_diagnostics_encrypted` as critical when a required table or column is absent or a nonempty `last_error` value remains plaintext.

Legacy checkout documents require both database migration and physical public-file cleanup. First dry-run and then apply `event-bookings:migrate-private-documents` and `product-orders:migrate-private-documents`. The dry run performs the same content inspection as apply mode: invoices must be genuine, passive PDFs within the size limit, while evidence and receipts must be genuine bounded JPG or PNG images whose extension, detected MIME type and dimensions agree. Reconcile every missing, unreadable, disguised, active-content or oversized source before applying. Apply mode copies only validated content and compensating-deletes any newly created private object if a later document or database commit fails, so a failed record cannot leave an unreferenced private copy. Verify the resulting private references, objects and backup before deletion. Next run `php artisan documents:purge-legacy-public` without `--apply` and review its event/product counts. The apply mode refuses to run while any booking or order still references a public path, deletes only files discovered inside the four allowlisted legacy invoice/evidence directories, verifies the directories are empty and writes aggregate started/completed audit events without filenames. Run `php artisan documents:purge-legacy-public --apply` only after approval, then rerun release readiness. The existing stable storage checks remain critical if either database references or orphaned physical public files survive, including after a partial deletion failure.

Waiting-list emails are capacity signals, not ticket holds. `events:dispatch-waitlist` runs every minute, expires old invitation windows and invites active entries FIFO without exceeding current stock after active invitations are counted. Reservation release also triggers an immediate check. The same command recovers an initial queue-handoff failure using the existing entry, window and encrypted unique job; it does not invite another attendee or consume another slot. Do not promise inventory to a recipient or extend a window manually; the customer must complete normal checkout. Contact values and dispatch errors are encrypted and unsubscribe links are signed. The existing `bookings:monitor-deliveries` command reports stuck or exhausted waitlist emails through the incident channel. If dispatch stops, verify the default queue and scheduler and let the durable entry recover; never bulk-mark entries notified without a corresponding delivered email.

Organizer guest invitations are private RSVP records, not paid tickets and not marketing-list subscriptions. Organizers must attest that they are permitted to contact every invited guest; do not bypass this control or upload a contact list whose source cannot be established. Guest contact values and delivery errors are encrypted, RSVP URLs expire, acceptance requires essential-processing consent, and marketing consent is a separate optional choice. Only accepted guests can be checked in. Event cancellation suppresses unsent mail and invalidates outstanding invitations. `guests:dispatch-invitations` runs every minute to reconstruct a lost initial queue handoff from the encrypted pending token; it reuses the same invitation/job identity, raises one stale incident and retires expired pending links. `bookings:monitor-deliveries` reports invitation jobs that are stuck or exhaust five attempts. Resolve the mail transport or recipient issue and then send a fresh invitation through the organizer guest-list screen; never edit token hashes, encrypted dispatch tokens, consent timestamps or delivery states directly. For bulk work, download the current `name,email,party_size` template, use each normalized email once and correct rejected row numbers in a new file; do not edit the non-PII import ledger. Successful source files are deleted after processing. `guests:prune-imports` removes expired failed sources from private storage. Guest exports require explicit RSVP/operations-use confirmation and expire under the shared private export policy; never copy them to public storage or share a signed actor link. Preview retention with `php artisan guests:apply-retention --json`. After policy approval, set `TICKET_GUEST_RETENTION_DAYS`, enable `TICKET_GUEST_RETENTION_ENABLED=true`, run another dry-run and only then allow scheduled `--apply`. Anonymization is irreversible and intentionally skips pending/failed delivery work.

Ticket resends are available from the authenticated buyer booking and organizer-owned booking screens. They always deliver to the original booking address; support must not alter the recipient or use the resend control to transfer ownership. A resend is rejected for unpaid, fully refunded, cancelled/cancellation-pending or inactive-ticket bookings. The queued job rebuilds the private invoice from the current ticket-unit ledger, so an old/replaced QR is not reintroduced; checked-in/revoked/refunded credentials and tickets accepted by a transfer recipient are omitted. `tickets:dispatch-resends` re-attempts a failed initial queue handoff every minute using the same request/job identity, while `bookings:monitor-deliveries` alerts on jobs stuck after processing begins or exhausted after delivery retries. Fix the queue, mail or private-document problem and let the durable request recover; do not create another request or manually mark one sent.

Ticket-transfer invitations are also durable default-queue deliveries. Creating the transfer records it before dispatch; the encrypted unique job retries transient mail failure five times and will suppress delivery if the transfer expires, is cancelled/superseded, or its event is inactive/cancelled. `bookings:monitor-deliveries` alerts on stuck or exhausted invitations. Never mark delivery sent or copy the one-time token from queue payloads; resolve the mail transport and let the existing encrypted job retry. The original holder's QR remains authoritative until the exact verified recipient accepts.

Organizer email verification uses the configured Laravel mail transport and a durable delivery ledger; it must never be replaced with a local SMTP socket, disabled certificate validation or a self-signed-certificate exception. Verification URLs are signed, expire after 60 minutes and are bound to the organizer's current normalized email hash, so changing the account email invalidates an outstanding link. The public resend form deliberately returns the same response whether or not an account exists, applies a two-minute durable cooldown and is route-throttled to reduce enumeration and abuse. `bookings:monitor-deliveries` alerts on a verification job stuck in processing or exhausted after five attempts. Fix the transport or recipient problem and request a fresh link; never edit the email hash, expiry, delivery state or verification timestamps directly.

Customer email verification follows the same delivery and security contract. The customer row is committed before dispatch, the job is encrypted and unique, the signed link expires after 60 minutes and binds both the delivery UUID and current normalized email hash, and only successful verification activates the account. The public resend response is deliberately generic and uses the same two-minute durable cooldown plus route throttling. Customer password-reset email also uses the configured Laravel transport rather than constructing an independent SMTP client. Treat stuck/exhausted customer verification in `bookings:monitor-deliveries` as an authentication incident; repair mail delivery and request a new link instead of reusing or editing an expired ledger row.

All application mail must use Laravel's configured transport and the shared configured-mail boundary. Do not add controller-level SMTP hosts, credentials, certificate exceptions or direct PHPMailer clients. The boundary rejects invalid recipients and missing/unreadable attachments before delivery and obtains the sender identity from managed settings; callers remain responsible for authorizing every private attachment before passing its resolved path. Contact-form bodies are escaped and a reply-to address is accepted only after email validation. Subscriber campaigns are immutable recipient snapshots with encrypted contact data and per-recipient delivery state. They fan out on the `default` queue and are globally bounded by `MAIL_CAMPAIGNS_PER_MINUTE` (60 by default); set this below the provider's verified allowance, keep the worker healthy, and use the recent-campaign table rather than resubmitting a slow campaign. `campaigns:dispatch-pending` retries the same unique fan-out job every minute when the initial handoff fails, while `bookings:monitor-deliveries` alerts on stuck or exhausted recipients. A recorded dispatch error or delayed campaign is not permission to create another campaign: restore the queue and let the durable parent recover. Do not edit encrypted addresses, counters or delivery states directly.

Visitor push broadcasts also run as durable campaigns on the `default` queue. A campaign snapshots only guests with an active browser subscription, encrypts its title/body/action at rest and fans out one unique delivery job per subscribed browser. Bound throughput with `PUSH_CAMPAIGNS_PER_MINUTE` (120 by default) below the verified provider allowance. The admin response means the campaign was durably accepted, not delivered; `campaigns:dispatch-pending` recovers the parent fan-out without creating another broadcast, and the recent-campaign table plus `bookings:monitor-deliveries` show downstream progress and incidents. An unsubscribed browser is recorded as failed without retrying; transient provider errors retry with backoff. Never resend an entire campaign merely because the request returned quickly, and never edit encrypted content or delivery counters directly.

VAPID credentials are deployment-managed secrets. Generate the pair once with the package CLI, store `VAPID_PRIVATE_KEY` in the selected secret manager, set a stable `VAPID_PUBLIC_KEY` and an HTTPS or `mailto:` `VAPID_SUBJECT`, then rebuild the configuration cache. Never paste, rotate or persist these values through the admin website and never expose the private key in logs or support screenshots. `ops:release-readiness` rejects a missing, weak, identical or insecure VAPID configuration.

Administrator-managed gateway, social-login, captcha, application-name and timezone changes persist only to their authoritative database rows. Web boot hydrates the corresponding SDK configuration for the current request; it does not rewrite `.env`, run `config:clear`, or invalidate the immutable configuration cache used by other requests and workers. Keep deployment-only credentials in the selected secret manager, rebuild cached configuration during a controlled release when those values change, and never reintroduce environment-file mutation or cache-clearing commands in an HTTP controller. After changing a database-managed integration, exercise its sandbox connection in a fresh request and restart long-lived workers only when the integration is used by queued jobs.

Online-gateway configuration blobs are encrypted with `APP_KEY`, and credential inputs are deliberately write-only in the administrator UI. Before the first release containing this contract, back up the database, run `php artisan gateways:encrypt-credentials --json`, review the pending count, then run `php artisan gateways:encrypt-credentials --apply --json`. The operation is transactional and idempotent. `ops:release-readiness` remains critical while any plaintext row exists. A blank credential field keeps the saved value; enter a replacement only during an authorized rotation. Losing or rotating `APP_KEY` without a framework-compatible decrypt-and-re-encrypt plan makes these credentials unreadable, so include gateway access in the application-key rotation drill and never copy decrypted values into tickets, logs or screenshots.

Database-managed SMTP, CAPTCHA and social-login secrets use the same write-only rule. Apply the secret-column expansion migration before conversion, run `php artisan settings:encrypt-secrets --json`, review the number of pending values, then run `php artisan settings:encrypt-secrets --apply --json`. The command is transactional and idempotent; release readiness fails until every configured value carries the encrypted envelope. Public site/client identifiers remain visible, while a blank secret/password input preserves the encrypted value. Exercise CAPTCHA and each enabled social callback after conversion. Application mail continues through Laravel's configured transport; verify a queued delivery through the production worker rather than treating the settings form as provider proof.

Maintenance mode never creates a public bypass URL. The administrator area remains reachable through the explicit maintenance-middleware exception, while public traffic is redirected to `/service-unavailable`. The legacy database bypass token is cleared by migration and on every maintenance update. Treat any reintroduction of a `--secret` argument or a bypass-token form field as a security regression. The controller invokes `down` and `up` with structured command arguments, checks the command result, and attempts to restore the prior runtime state if persisting the new setting fails.

Event share previews are generated as cacheable 1200×630 PNGs from the event image or the bundled licensed fallback. Validate a deployed public event with Facebook, X and WhatsApp before launch; local rendering and metadata do not prove that provider crawlers can reach production. Draft and archived event IDs intentionally return no public detail or share card. Use only the authenticated administrator/owner preview link while editing; it is marked `noindex` and must never be substituted for the public URL in campaigns.

Account-reset, contact, manual booking/order status, balance-adjustment and manual withdrawal messages use `application_mail_deliveries` instead of sending inside web requests. Recipient, subject, body, attachments, reply-to and failure details are encrypted; the ledger retains only hashed recipient lookup plus non-secret kind/source/actor evidence. A successful web response means the message was durably queued, not that the recipient provider accepted it. The default worker retries five times with backoff and `bookings:monitor-deliveries` escalates stuck or exhausted rows. Repair the queue, transport or referenced private document and allow the existing job to retry; never decrypt or edit message rows manually, and never tell a user delivery succeeded solely from the request response.

Corporate registration is a separate admission-interest workflow, not a paid ticket or a substitute for payment evidence. Only publish a form after reviewing its purpose, privacy notice, required fields, ticket-specific assignments and approval mode. Organizer templates are versioned snapshots: applying one replaces the current question set, clears event-specific ticket assignments and returns a published form to draft, so re-check every question and registration type before publishing. Agenda sessions must fall inside the event schedule; review registration-type restrictions, required status, overlaps and capacity before opening registration. Once a session has selections, it may only have capacity increased—replace it and contact attendees for other changes. Never reduce capacity below active selections or silently cancel a populated session. Imports use pipe-separated `attendee_session_ids` from the current template, and session capacity is enforced through the same locked submission path as the public form. A company invoice may be issued only after approval and only when every attendee has a supported registration type. Issuance reserves inventory until the due date; share the private PDF only with the authorized company contact. Before using **Mark paid & issue tickets**, reconcile the exact amount and reference against the bank/provider record and retain a concise internal note. Never mark an invoice paid from an email claim or purchase-order document alone. The operation is one-way: it creates the financial ledger identity and attendee tickets, while a repeated request is idempotent. The scheduler runs `registrations:expire-invoices` every fifteen minutes to expire overdue invoices and restore inventory. Sponsor allocations must be created only for an authorized sponsor contact; the sponsor portal is an expiring private credential, must not be posted publicly, and every attendee contact requires the sponsor’s source attestation. Cancelling an allocation invalidates all incomplete attendee links. Configure `EVENT_REGISTRATION_ALLOCATION_DAYS` to the shortest practical window and treat stuck or five-attempt allocation mail failures reported by `bookings:monitor-deliveries` as incidents. Minimize collection of sensitive data, never place secrets or payment-card data in custom questions, and do not extract encrypted answers directly from the database. Manual decisions must be made through the organizer registration screen so the actor, reason and status transition are audited. An approved registration does not issue a ticket or guarantee admission until the invoice is verifiably paid or another documented ticket-issue workflow completes. Submission, approval, rejection and event-cancellation messages have a durable ledger and run on the default queue; `bookings:monitor-deliveries` treats a stuck job or five exhausted attempts as a critical incident. Resolve the mail transport or recipient problem before retrying and never mark a notification sent manually. Cancelling an event cancels submitted/approved registrations and queues cancellation notices. For bulk imports, always download a fresh template after form or agenda changes, use one row per attendee and one registration key per buyer/company group, provide `attendee_ticket_id` and `attendee_session_ids` when the template includes them, and never disable the source-contact attestation. Correct rejected row numbers in a new file; do not edit import ledgers or encrypted submissions. Successful sources are deleted after processing. Failed files remain private only until `EVENT_REGISTRATION_IMPORT_RETENTION_DAYS`; `registrations:prune-imports` removes expired sources while retaining non-PII results and audit history. Registration exports require the organizer’s explicit privacy-use confirmation, exclude anonymized records, run asynchronously, remain on private storage, use short-lived signed actor-owned downloads, and expire under `DATA_EXPORT_RETENTION_DAYS`; do not copy them to public storage or share signed links. Preview retention with `php artisan registrations:apply-retention --json`. After legal/privacy approval, set `EVENT_REGISTRATION_RETENTION_DAYS`, enable `EVENT_REGISTRATION_RETENTION_ENABLED=true`, run another dry-run, and then allow the daily scheduled `--apply` command. Anonymization is irreversible, audit-recorded, preserves non-personal operational history, and skips registrations with unresolved delivery. Out-of-cycle privacy requests still require controlled operational handling. Corporate exports report ticket-unit identity, status, check-in time and the verified enrolled gate device as of the request timestamp; request a new export for later event-day scans rather than treating an old file as live attendance.

Badge printing and website embedding are operationally sensitive corporate controls. Print badges only after ticket issuance; their QR is the live admission credential, so discard spoiled copies securely and never email a full badge batch. Before enabling an embed, obtain the exact HTTPS origin from the partner, enter only that origin, preview it on the partner page and verify that an unlisted test page is blocked by the browser. Do not add wildcards, URL paths or third-party preview/proxy domains. If a partner site is compromised or the integration ends, disable the embed immediately; existing first-party registration remains available. The embed POST signature is short-lived and regenerated with each page load, so never extract or hard-code its action URL outside the supplied iframe snippet.

Paystack product refunds are queued by the order refund interface and processed by `payments:process-refunds`. Finance must wait for `processed` from the signed webhook or `payments:reconcile-refunds`; the local order, earnings and inventory do not change while the refund is pending, indeterminate or failed. Never record a second manual refund for an order with a provider refund in flight.

For manual product payments, **Record full refund** remains an accounting and inventory reconciliation control, not a money-moving action. Finance must complete or independently verify the bank or cash-desk refund first, then enter its unique external receipt/reference and an evidence note. For a hardened Paystack order, the same interface clearly becomes **Request Paystack refund** and does move money through the queued provider workflow. In both paths, unfulfilled orders must restore reserved physical inventory; fulfilled orders may only be restocked after returned goods are verified. A terminal successful refund creates transaction type 7 (`Product Refund`), reverses paid platform revenue once, cancels the order and writes an audit record.

Product payment receipts and invoices must use `PRODUCT_ORDER_DOCUMENT_DISK=local` or another private-capable disk; never select the public disk or a disk rooted below `public/`. Before the first hardened release, audit and migrate historical files:

```bash
php artisan product-orders:migrate-private-documents
php artisan product-orders:migrate-private-documents --apply --delete-public
php artisan event-bookings:migrate-private-documents
php artisan event-bookings:migrate-private-documents --apply --delete-public
php artisan tickets:purge-public-qr-artifacts
php artisan tickets:purge-public-qr-artifacts --apply
```

For each document family, the command without options is a validating dry run, not a filename-only preview. It rejects disguised or active-content PDFs, non-image evidence, extension/MIME/dimension mismatches, unreadable input and configured size or pixel-limit violations before any copy. Apply mode copies every validated legacy document and audits the record; if any later validation, database operation or commit fails, the command removes private objects created during that record before reporting failure. `--delete-public` removes exposed copies only after all selected imports succeed. The event migration also clears the historical non-PDF evidence value that was incorrectly copied into the invoice column. Run the QR purge only after validating the new private invoices because legacy SVGs are reusable admission credentials. `ops:release-readiness` fails while either document disk is public, a legacy product/event document reference remains, or a public QR SVG still exists.

Paid event email/SMS, product-order email confirmation and manual booking/order rejection-notice jobs run on the `payments` queue and persist their state in `booking_deliveries` and `product_order_deliveries`. A manual offline approval commits its paid status, financial ledger/accounting and pending fulfillment record in one database transaction; if the fulfillment record cannot be stored, the entire approval rolls back. A manual rejection likewise commits the rejected status, exact-once inventory release and pending rejection-notice identity atomically; if that delivery record cannot be stored, the rejection rolls back. Admin and organizer event approvals then use the same queued invoice, ticket, email and SMS pipeline as verified online payments rather than generating documents or sending approval mail in the request. Rejection messages use encrypted unique jobs and the shared configured mail transport rather than request-bound SMTP. `payments:dispatch-fulfillments` runs every minute and reconstructs an initial approval or rejection queue handoff that failed after the decision committed, using the same encrypted unique job and durable delivery identity. Dispatch attempts are distinct from provider-delivery attempts. The existing `bookings:monitor-deliveries` schedule covers both families after processing begins; a stuck or five-attempt exhausted delivery is a critical incident and must be reconciled before manual intervention. Restore the queue and let a still-pending delivery recover. Once an SMS job has contacted the provider, use the evidence-gated `tickets:recover-sms-delivery` workflow instead—never replay an ambiguous SMS automatically. Do not create another booking/order or manually mark any confirmation or rejection notice sent.

## Release sequence

Use `docs/production-launch-evidence-checklist.md` as the release-control sheet
for ownership and evidence collection. The detailed procedures in this runbook
remain authoritative for execution and incident handling.

1. Back up the database and record the deploy revision/release directory.
2. Install locked backend and frontend dependencies on the supported PHP and Node runtimes, audit the installed graph, and build immutable frontend assets:

   ```sh
   composer install --no-dev --classmap-authoritative --no-interaction
   composer audit --locked --abandoned=fail --no-interaction
   npm ci
   npm audit --audit-level=high
   npm run build
   ```

3. Run the static preflight before traffic moves:

   ```sh
   php artisan ops:release-readiness --configuration-only
   ```

   This preflight is fail-closed. It verifies both required transactional tables and safety-critical columns, so a partially migrated schema cannot receive traffic. It also verifies that the required Vite manifest entry resolves to a readable file inside `public/build`; missing, malformed or out-of-root assets block the release.

4. Run migrations once:

   ```sh
   php artisan migrate --force
   ```

   The platform-earnings migration requires zero or one historical `earnings` row. An empty installation is seeded safely. If multiple rows exist, migration stops deliberately: finance must establish the provenance of each balance and reconcile them to exactly one approved row before retrying. Never automatically sum or delete these rows. Release readiness subsequently requires exactly one live row with `singleton_key=1`, so privileged deletion or malformed finance evidence also blocks traffic.

5. Build/cache application state:

   ```sh
   php artisan config:cache
   php artisan route:cache
   php artisan view:cache
   ```

6. Point the web release symlink at the new release, then restart workers gracefully:

   ```sh
   php artisan queue:restart
   supervisorctl reread
   supervisorctl update
   supervisorctl restart tica-payments:*
   supervisorctl restart tica-default:*
   ```

7. Wait at least two scheduler cycles so every queue heartbeat is consumed, then require:

   ```sh
   php artisan ops:release-readiness
   curl --fail --silent https://YOUR_HOST/health/live
   curl --fail --silent https://YOUR_HOST/health/ready
   ```

8. Run a low-value sandbox/smoke purchase and verify payment intent, booking, ticket delivery and reconciliation records before declaring the release healthy.

## Alert receiver contract

The incident webhook receives JSON over HTTPS with:

- `X-Tica-Alert-Id`: unique delivery identifier;
- `X-Tica-Signature`: lowercase HMAC-SHA256 of the exact request body using `OPS_INCIDENT_WEBHOOK_SECRET`;
- `key`, `severity`, `title`, `environment`, `app_url`, `occurred_at`, and a redacted `context` object.

The receiver must compare signatures in constant time, reject stale timestamps, deduplicate by alert ID, and page the assigned operator. Alerts are cooldown-deduplicated in shared cache; delivery failures are still written to the application log.

## Routine checks

- `/health/live`: process liveness only.
- `/health/ready`: database, shared cache/session write-read reachability, cache lock coordination, worker heartbeat, backlog and failed-job readiness. Its temporary shared-state probes use an isolated session handler and are deleted immediately. A 503 removes the instance from service; the anonymous response never exposes which dependency failed.
- `php artisan ops:monitor-queues --json`: queue details for incident triage.
- `php artisan ops:monitor-webhooks --json`: Paystack and Flutterwave rejection, failure and stuck-receipt health.
- `php artisan payments:monitor-intents --batch-size=100`: release bounded expired reservations, expire abandoned intents and report stuck event/product payment intents. The command counts the complete stale population but includes only the oldest 1–500 records from each family in the incident payload; increase the batch only for an evidence-led investigation, never to turn an outage into an unbounded alert.
- `php artisan payments:reconcile-paystack --date=YYYY-MM-DD`: compare successful Paystack charges with durable intents, bookings and gateway-scoped sale-ledger identities. It runs daily at 02:15 for the previous day and is isolated by default, so a simultaneous manual invocation exits unsuccessfully rather than creating competing evidence. Provider pages are consumed sequentially, and local intents and ledgers are loaded only for the references in the current page. Local-only detection is a bounded database scan against the entries already recorded for that run; it does not materialize the full provider day or local intent population in memory. A provider failure keeps its detailed text only in the encrypted run diagnostic and emits only exception type/code metadata to the incident channel.
- `php artisan payments:reconcile-flutterwave --date=YYYY-MM-DD`: perform the equivalent Flutterwave comparison in major currency units. It uses the same isolated, bounded page/chunk and privacy-safe failure contract and runs daily at 02:30; review `gateway_only`, `local_only`, booking/status, amount/currency and ledger-identity mismatches in **Transactions → Payment reconciliation** before finance close.
- `php artisan payments:reconcile-paystack-settlements --from=YYYY-MM-DD --to=YYYY-MM-DD`: reconcile Paystack bank settlements and their transaction breakdown. Settlement-list and transaction pages are consumed sequentially, local intent/ledger lookups are bounded to the current provider page, counters are committed page by page and transaction retries cannot double-count them. The command is isolated by default across scheduled and manual invocations; a competing run exits unsuccessfully instead of interleaving delete/rebuild pages. An oversized settlement range aborts before the first partial range is persisted; an oversized transaction breakdown leaves that settlement explicitly failed with no partial page evidence.

All three provider scans fail closed if the provider would require more than 1,000 pages. A ceiling failure is a **failed run or command**, not evidence that the unvisited provider population is absent; it must never be used to approve `local_only` findings, settlement totals or finance close. A failed charge run retains only the counters and entries truthfully processed before the failure for investigation; a failed settlement retains only previously completed page counters, never the oversized page. Resolve the provider/date-range volume problem, rerun the complete period successfully and use only that completed result as finance-close evidence.
- `php artisan payments:process-refunds --limit=20`: submit a bounded batch of newly approved Paystack and Flutterwave refunds. The command is isolated by default across scheduled and manual invocations and exits unsuccessfully when another run owns the lock; it must not be replayed blindly after an ambiguous outcome.
- `php artisan payments:reconcile-refunds --limit=50`: refresh a bounded batch of non-final refunds from their provider before any manual intervention. It is also isolated by default. A lookup exception is stored in the refund's encrypted diagnostic field and advances its update timestamp so one broken record cannot monopolize every oldest-first batch; application logs contain only safe exception type/code metadata. Repeated failure still requires provider evidence and finance review, never a second refund submission.
- `php artisan payouts:reconcile-paystack --limit=100`: verify the oldest due unresolved Paystack transfers in a bounded 1–500-record batch. The command is isolated by default across scheduled and manual invocations; failed lookups keep the raw provider diagnostic only in the encrypted transfer field, move behind untouched due work and expose only safe exception type/code metadata in logs, audit records and incidents. Repeated verification failure moves the existing transfer to `needs_attention`; never submit a replacement payout.
- `php artisan payments:dispatch-fulfillments`: recover committed paid event email/SMS and product-order email confirmations whose initial payments-queue handoff failed. It reuses the durable delivery and encrypted unique job identity, records queue-dispatch attempts separately from provider attempts and raises one stale incident. SMS recovery applies only before the provider job starts; ambiguous provider outcomes still require `tickets:recover-sms-delivery` with external evidence. Restore the payments worker and let the pending record recover; do not create a duplicate order or manually mark the confirmation sent.
- `php artisan payouts:dispatch-pending`: recover committed Paystack payout transfers that remain queued because their payments-queue handoff failed, and reconstruct missing organizer/finance status-notification jobs from the committed transfer state. This runs every minute and raises one critical stale incident per transfer/status. Never create another payout, alter the withdrawal status or release its reserved funds; restore the affected queue and let the same unique transfer/job identity dispatch. Audience delivery markers prevent an already-recorded notification from being sent again.
- `php artisan events:dispatch-waitlist`: expire old ticket-availability windows, queue capacity-bounded FIFO invitations and recover committed invitation windows whose initial default-queue handoff failed. Recovery reuses the same entry and encrypted unique job; never create another invitation or advance the FIFO list solely because the queue was unavailable.
- `php artisan events:dispatch-cancellation-notices`: recover committed buyer cancellation/refund-outcome notices whose initial default-queue handoff failed. It reuses the existing notice and encrypted unique job, preserves separate dispatch and mail-delivery attempts and raises one privacy-safe stale incident. Restore the queue and let the original notice recover; do not create a replacement or manually mark a buyer notified.
- `php artisan tickets:dispatch-transfers`: recover committed ticket-transfer invitations whose initial default-queue handoff failed. It reuses the encrypted pending token and same transfer/job identity every minute; stale records raise one privacy-safe incident. Do not create a replacement transfer for a queue outage because doing so supersedes the existing invitation.
- `php artisan tickets:dispatch-resends`: recover committed ticket-resend requests whose initial payments-queue handoff failed. It reuses the same request and encrypted unique job identity, records dispatch attempts separately from mail-provider attempts and raises one privacy-safe stale incident. Restore the queue and let this command recover the request; do not bypass the cooldown or create a duplicate resend.
- `php artisan guests:dispatch-invitations`: recover committed guest RSVP invitations whose initial default-queue handoff failed. It reuses the encrypted pending token and same invitation/job identity; stale records raise one privacy-safe incident and expired links are retired without dispatch.
- `php artisan accounts:dispatch-verifications`: recover committed organizer and customer email-verification deliveries whose initial default-queue handoff failed. It rebuilds the signed link from the current delivery/account state, reuses the same unique job identity, suppresses expired pending rows and raises one privacy-safe stale incident.
- `php artisan mail:dispatch-pending`: recover committed shared application-mail deliveries whose initial default-queue handoff failed. It reuses the encrypted delivery payload and same unique job identity, keeps dispatch attempts separate from mail-provider attempts, and raises one privacy-safe stale incident.
- `php artisan bookings:monitor-deliveries`: detect individual durable deliveries that never leave pending, plus stuck/exhausted booking, product, application-mail, subscriber/push campaign, cancellation, waitlist, guest-invitation and registration-status delivery. Pending-handoff coverage includes booking email/SMS, ticket resends/transfers, product confirmations, organizer/customer verification, application mail, cancellation/registration notices, guest/waitlist invitations and sponsor allocations. A pending incident means the queue handoff or worker did not begin within the configured window; verify queue connectivity and worker health before retrying the exact idempotent delivery. Campaign fan-out is intentionally monitored at aggregate/worker level to avoid one alert per recipient.
- `php artisan campaigns:dispatch-pending`: re-attempt the same unique subscriber/push campaign fan-out job after an initial queue-handoff failure or an exhausted recipient fan-out. The parent returns to `pending`, retains its immutable recipient ledger and dispatch error, and the command emits one aggregate stale-campaign incident. Recipient jobs remain unique, so restore the default queue and let the existing campaign resume; do not create a replacement campaign.
- `php artisan registrations:apply-retention --json`: preview corporate registrations eligible for privacy anonymization; add `--apply` only after policy approval.
- `php artisan registrations:prune-imports`: delete expired private registration-import sources while retaining row results and audit history; this runs daily.
- `php artisan registrations:dispatch-allocations`: recover committed sponsor-access and allocated-attendee invitation jobs whose initial queue handoff failed. It runs every minute, reuses the encrypted pending token and same unique delivery identity, and raises a privacy-safe stale incident. Do not create a replacement allocation solely because the queue was unavailable; restore the default worker and allow this command to recover the existing record.
- `php artisan registrations:dispatch-notifications`: recover committed registration submitted/approved/rejected/cancelled notices whose initial default-queue handoff failed. It preserves the existing notification and encrypted unique job identity, separates dispatch attempts from provider attempts and raises one privacy-safe stale incident. Restore the queue and let the original notice recover; do not repeat the organizer decision or create another notification.
- `php artisan guests:apply-retention --json`: preview guest invitations eligible for privacy anonymization; add `--apply` only after policy approval.
- `php artisan guests:prune-imports`: delete expired private guest-import sources while retaining non-PII row results and audit history; this runs daily.
- `php artisan exports:run-schedules`: claim due recurring booking schedules under database locks and queue the same private point-in-time exports used by one-time requests; this runs every minute and does not distribute attachments by email.
- `php artisan exports:dispatch-pending`: recover unexpired one-time private exports whose initial queue handoff failed and emit one stale-export incident after the bounded delay. This runs every minute. Restore the default queue and let the command re-dispatch the existing unique job; never create a replacement export merely because the original remains queued.
- `php artisan exports:notify-ready`: create one durable completion email for each ready, unexpired private export. The message contains an actor-owned signed URL that expires with the file and still requires the requesting account to authenticate. The command runs every minute, stores encrypted creation errors and raises one privacy-safe stale incident; the shared `mail:dispatch-pending` command recovers a lost mail-queue handoff after the delivery ledger has been committed. Never email the export as an attachment, generate a public link, or copy a link between accounts.
- `php artisan imports:dispatch-pending`: recover unexpired private guest and corporate-registration imports whose initial queue handoff failed and emit one stale-import incident. This runs every minute. Preserve the original private source, restore the default queue and let the existing import resume; do not ask the organizer to upload the same PII again while its ledger remains queued.
- `php artisan audit:apply-retention --json`: preview audit records older than `AUDIT_LOG_RETENTION_DAYS`; after documented controller approval set `AUDIT_LOG_RETENTION_ENABLED=true` and permit the scheduled `--apply` run. Never delete or update audit rows directly. Transaction-authorized administrators can request private point-in-time evidence exports from **Transactions → Audit history**; links remain actor-owned, signed and short-lived.
- `php artisan schedule:list`: verify payment, payout, delivery, scanner and export tasks.
- Review failed jobs, reconciliation mismatches, stuck payment intents, failed booking deliveries and expired exports daily.
- Booking exports are point-in-time finance reports: ledger identity, financially applied refunds and matched settlement evidence are bounded by the stored request timestamp. Generate a new export after later refunds or reconciliation; do not edit a previously generated file into a live ledger report.
- Review recurring-export consecutive failures in the owner’s export-history screen. Pause a broken schedule while correcting its filters or data availability; never work around a failure by copying private files into public storage.
- Finance statements above `DATA_EXPORT_IMMEDIATE_FINANCE_ROWS` are queued as private CSV/XLSX exports and use the request-time maximum transaction ID as their immutable ledger boundary. Review them in organizer export history, allow the default worker to finish, and generate a new statement when later transactions must be included. Large PDF statements are deliberately rejected; do not increase PHP memory limits or move generated files to public storage as a workaround.
- Review and resolve grouped incidents at `/admin/operations/incidents`; resolution requires a note and never suppresses a new occurrence.
- Review privacy-safe gateway receipt metadata at `/admin/operations/webhooks`. Raw payloads, customer data and gateway references are never retained; reference and body fingerprints are one-way hashes. Records older than `WEBHOOK_RECEIPT_RETENTION_DAYS` (90 by default, minimum 30) are deleted daily by `ops:prune-webhook-receipts`.
- Follow `docs/privacy-and-data-governance.md` for the data map, request handling, vendor review and breach process. Release readiness fails without an accountable owner, versioned policy, bounded active retention and current launch/DPA evidence; do not fabricate those attestations to clear the gate.
- Review customer deletion cases under **Customer Management → Privacy Requests**. Verify requester identity and inspect every relevant data family before moving a case under review. A fulfilled decision requires a non-secret evidence reference and archives the account, but deliberately preserves financial, ticket, security and audit history. Record lawful-retention exceptions and any separately approved anonymization work in the resolution; never mark a case fulfilled merely because the account was deactivated.
- Follow `docs/accessibility-release-standard.md` for the WCAG 2.2 AA journey matrix. Release readiness requires a current report plus separate keyboard, screen-reader, checkout and scanner verification; automated scans alone cannot clear the gate.
- Follow `docs/backup-and-recovery-runbook.md`: verify database and private-file backup completion daily and perform a documented isolated restore drill at least quarterly. `ops:release-readiness` fails when ownership, encrypted/off-site coverage, bounded RPO/RTO or current drill evidence is absent.

## Queue incident response

1. Do not replay failed payment/refund/payout jobs blindly. Inspect their stable gateway reference and current provider state first.
2. Confirm Redis and database reachability, then inspect worker logs and `queue:failed`.
3. Restore `payments` workers before `default` workers.
4. Run the relevant reconciliation command before retrying any ambiguous money movement.
5. Use `queue:retry <id>` only after proving the job is idempotent and the external outcome is known.
6. Require `/health/ready` and `ops:release-readiness` to recover before closing the incident.

## Rollback

Application rollback means moving traffic back to the previous immutable release and restarting workers against that release. Do not automatically roll back a database migration that has already accepted transactional data. Use a forward repair unless the migration is explicitly proven reversible with no new writes. Preserve failed jobs, payment intents, audit logs, reconciliation runs, exports and incident logs as evidence.
